# Lane L56 — T8 mcp: Measured MCP overhead vs direct CLI invocation

Compiled 2026-08-25 · Method: web_search + direct reads of primary sources (spec pages, vendor engineering posts, peer-reviewed papers, benchmark repos). No local measurement possible (read-only lane, no shell); all numbers below are cited measurements, arithmetic derivations marked.

## Measured digest (the three questions asked)

**Roundtrip latency, stdio vs HTTP (Benchivo controlled benchmark, run+published 2026-08-10; Node 22.23.2, Apple M4, MCP protocol 2025-06-18, byte-identical no-op handlers, 400 calls/size, harness + raw JSON published):**
- Warm RTT p50 @1KB: stdio **0.020 ms**, HTTP keep-alive 0.117 ms, HTTP no-keep-alive 0.157 ms (@16KB: 0.070/0.125/0.162; @256KB: 0.907/0.984/1.403 ms — gap narrows to 8%). 1KB p99: 0.121/0.395/0.549 ms.
- Session cold-start ready p50: stdio 31.26 ms vs HTTP 36.6–36.8 ms (≤5 ms apart; stdio has no readiness signal, so process boot lands inside first call).
- 8 concurrent calls, batch wall p50: stdio 0.051 ms vs HTTP keep-alive 0.355 ms (stdio syscall batching wins; irrelevant once server does real work).
- Bottom line: **~0.1 ms/call gap**; 200 calls cost <30 ms total. Transport choice is a deployment decision, not a performance one. Any real network RTT (1–10 ms) dwarfs it. Keep-alive/connection reuse is the only HTTP knob that matters.
- Spec grounding: stdio = newline-delimited JSON-RPC over child stdin/stdout; Streamable HTTP (2025-03-26+) = POST per message, response JSON or request-scoped SSE stream; the old SSE-only transport is deprecated.

**Token overhead, MCP envelopes vs plain CLI:**
- Per-call JSON-RPC envelope (`{"jsonrpc","method":"tools/call","params":{name,arguments}}` + `{content:[{type:text,text}]}` wrapper): ≈250 bytes ≈ **~60–80 tokens/call round trip** [arithmetic from spec schema] — real but minor.
- Catalog tax dominates: eager `tools/list` injection measured at **≈33,700 tokens for 72 tools** vs ≈800 tokens when only the task-relevant tool is exposed (**≈97% avoidable**) (mcp-turnstile BENCHMARK.md, accessed 2026-08-25); live-server extremes: 88-tool Amplitude server ≈140k tokens, 65 servers/552 tools ≈147k tokens = 73.5% of a 200k window (mcpgate.de, accessed 2026-08-25). Anthropic bills tool definitions as input tokens on every request (docs.anthropic.com pricing).
- CLI comparison point (mcp-vs-cli-bench README): "Connecting a tool catalogue over MCP places every tool's schema in the model's context. Exposing the same capability through a command-line tool places a command string there instead." A documented CLI costs one command-string + help text (tens–hundreds of tokens) and raw stdout with no wrapper. Where MCP loses further: intermediate results must round-trip through the model twice per handoff (Anthropic Drive→Salesforce example: 150,000 tokens direct-tool-calling vs 2,000 with code execution = **98.7% reduction**, posted 2025-11-04).
- Attribution (peer-reviewed): ProMCP (Findings of ACL 2026, pp. 39476–39487, DOI 10.18653/v1/2026.findings-acl.1967; 20 servers/169 tools): custom clients spend **56–72% of tokens and 60–67% of latency on planning + schema injection**; OTS clients >85% of latency in answer synthesis; **tool execution is negligible everywhere**. arXiv:2511.07426 (instrumented Cline host, 820 tasks): MCP sessions are prompt-heavy — completion:prompt ratio 2–30× lower than ordinary LLM traffic; recommends parallel/batched tool calls and abort loops.
- Direct MCP-vs-CLI measurement exists but numbers pending publication: Lamb-Project/mcp-vs-cli-bench (GPL-3.0+, Zenodo DOI 10.5281/zenodo.21851992): one fixed GitHub workflow × 7 scaffoldings × 5 models, official GitHub MCP server vs `gh` CLI, 54 cells, state-read-back scoring; "results collected", manuscript in submission (README accessed 2026-08-25).

**Verdict:** Top pick: stay CLI-first — expose capabilities as documented CLIs and reach for an MCP server only when a second consumer, separate deployment cadence, credential-isolation boundary, or genuine remoteness appears; when you do, use stdio locally (transport deltas are ~0.1 ms/call, i.e. noise next to inference) and Streamable HTTP only for shared/remote surfaces with connection reuse. The measured lever is tokens, not microseconds: cap and lazily disclose tool schemas (97% catalog reduction shown), avoid passing large intermediates through the model (98.7% reduction via code execution), and re-check mcp-vs-cli-bench's published matrix (Zenodo 10.5281/zenodo.21851992) for head-to-head numbers once the manuscript lands. Integration sketch for our S-A stack: keep graphifyy/tantivy/sqlite-vec pipelines callable as plain Python CLIs for the agent; wrap only stable query seams in one small stdio MCP server with `search_tools`-style discovery, hard result-size caps, and tokenizer-counted schema budget reviewed per release.
