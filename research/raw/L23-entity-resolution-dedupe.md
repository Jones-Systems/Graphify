# Lane L23 — T4 Entity Resolution: `dedupe` (dedupe.io OSS) assessment
Investigated 2026-08-25. Scope: maintenance state, Python 3.13 compat, active-learning fit for person/org entities across the 18 repos, scaling limits vs Splink.

## Verified key facts
- **Maintenance**: latest release **3.0.3 uploaded 2024-08-15T14:31Z** (PyPI JSON) — **no release in ~24 months** as of 2026-08-25. Maintainers Forest Gregg/Derek Eder (DataMade); repo ~4.5k stars/576 forks; ~14K weekly PyPI downloads; releases feed shows nothing newer than v3.0.3. Hosted **Dedupe.io SaaS was shut down 2023-01-31** (dedupe.io FAQ) — reduced commercial stake in OSS upkeep. Status: stable but stewardship-mode, no release cadence.
- **Python 3.13 (x86_64 Linux)**: works with two caveats. `dedupe` itself ships **cp313 manylinux_2_5 x86_64 wheels** (verified file list, 2024-08-15). Pure-Python deps fine: categorical-distance 1.9 (py3-none-any), highered 0.2.1, simplecosine 1.2 (py2.py3-none-any). **doublemetaphone 1.2 has cp313 manylinux wheels**. **affinegap tops out at 1.12 (wheels ≤cp39)** and **dedupe-Levenshtein-search 1.4.5 (≤cp311)** → both compile from sdist on 3.13 (needs Cython+gcc; build once into a wheelhouse). scikit-learn unpinned; **sklearn ≥1.6 supports CPython 3.9–3.13** (sklearn v1.6 notes, Dec 2024). requires-python >=3.8, MIT.
- **Active-learning workflow**: `prepare_training(data, sample_size)` → `console_label()` terminal pair-labeling → `train()` → `write_settings`; `StaticDedupe` reuses the trained model; learned blocking predicates plus Text/Categorical/custom variable types; `recall_weight` tunes precision/recall. Fits our no-local-LLM/no-cloud-keys constraint (human labels bootstrap the model). Watch-outs: keep labeled sets lean — issue #940 reports steep `prepare_train` slowdown already at thousands of labels; training sample must be representative.
- **Scaling**: in-memory design; `partition()` officially "small to moderately sized datasets" (docs.dedupe.io API docs); MemoryError reported at 180k rows on a 256 GB box during clustering (issue #480); millions of records require DIY candidate-pair generation + batched `score()` with Postgres-backed blocking (pgsql_big_dedupe_example). Comfortable ceiling ~1e5–1e6 records with tight blocking. Clustering graph is RAM-resident → collides with our MemAvailable ≥ 3072 MiB burst floor on large corpora.
- **Splink comparison** (baseline; deep dive owned by L22): **splink 4.0.16**, **MIT** license (LICENSE + pyproject verified), Fellegi-Sunter EM **unsupervised** (no labels needed), DuckDB default backend, official claim "million records on a laptop in around a minute", 100M+ via Spark/Athena; awards activity through 2025 → actively maintained. Out-of-core execution respects our RAM floor. Documented weak spot: single-column name-only linkage ("bag of words") is explicitly not its design center — relevant to org-name matching where dedupe's arbitrary comparators (doublemetaphone, token-based) shine.

## Verdict (≤3 lines)
Top pick for T4 backbone: **Splink 4/DuckDB** — MIT, actively maintained, out-of-core within our 3 GiB RAM-burst floor, scales far past dedupe's ~1e5–1e6 in-memory ceiling. Keep **dedupe** as a tactical add-on only where its interactive active-learning bootstraps scarce labels (org-name fuzzy comparators) and corpora stay ≤~200k records; its 24-month release gap means pinning + self-built wheels (affinegap/Levenshtein_search sdists on py3.13).
Integration sketch: extract person/org tables from graphifyy node-link JSON → run dedupe console_label sessions once to produce portable labeled-pair JSON → use those labels to calibrate/validate a Splink Fellegi-Sunter model (blocking on normalized name tokens + type), keeping all compute local and offline.
