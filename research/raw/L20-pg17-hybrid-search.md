# L20 — tsvector+pgvector hybrid search on the existing PostgreSQL 17 instance

Investigated 2026-08-25 by lane L20 (T3 hybrid). Question: should search for the 18-repo research corpus route through the already-running PostgreSQL 17 service in ~/Projects/Alpha-worktrees/compass-build-p0 instead of per-repo file-local stores (LanceDB-class)?

## Local ground truth (verified from the worktree, 2026-08-25)

- Runtime: portable PostgreSQL 17.11 (`tools/pg/usr/lib/postgresql/17/bin/postgres -D data/pg17 -p 5499 -k /tmp`, per `data/pg17/postmaster.opts`). Server debs pinned `postgresql-17_17.11-0+deb13u1_amd64.deb`. Upstream current minors 18.6/17.11 released 2026-08-13.
- Config is near-default: `shared_buffers=128MB`, `max_connections=100`, `work_mem` unset (4 MB), `maintenance_work_mem` unset (64 MB), no `shared_preload_libraries`, empty `postgresql.auto.conf`. WAL shows the cluster actively serving right now.
- NO vector extension exists in the portable prefix yet (only core tsvector objects under lib/bitcode); adding pgvector is a prerequisite either way.
- The cluster already carries a heavy workload (BUILD-WORKNOTE, updated 2026-08-24: member_votes ~10.95M rows, contribution_line ~66.48M lines, politicians 19,501, statements 8,750). Research indexes MUST live in a separate `research` DB + role inside the cluster, never injected into the `compass` DB, so compass backups/nightly dumps and ingest latency stay untouched.
- Compass planning docs already ratified Postgres FTS + pg_trgm as the search backend (doc 09 sec.7 S-A / D15-2 / PO-17: websearch_to_tsquery, GIN tsvector columns, trigram names) and the schema DDL was verified loading clean on this PG17 build (doc 02 sec.14, verification dated 2026-08-23).

### Verdict
Top pick: pgvector 0.8.6 + built-in tsvector FTS fused with RRF(k=60) inside the existing compass-pg :5499 cluster as an isolated `research` DB under a cgroup memory cap - beats file-local stores for cross-repo, metadata-joined retrieval with zero new services.
Why: both legs are permissively licensed and already ratified patterns here (FTS D15-2); pgvector is actively maintained through 2026-07; at our <=~1M-chunk scale a halfvec HNSW stays well under ~1 GB on disk with RAM bounded by MemoryHigh/MemoryMax.
Sketch: dpkg-deb -x the PGDG postgresql-17-pgvector 0.8.6 trixie deb into tools/pg (same layout trick as the existing server debs) -> CREATE EXTENSION vector in new `research` DB -> chunks(repo, path, body, tsv tsvector GENERATED ALWAYS AS ... STORED, emb halfvec(768)) with GIN(tsv) + HNSW((emb)::halfvec_cosine_ops, m=16, ef_construction=64) -> per query: SET LOCAL hnsw.iterative_scan = relaxed_order; two ranked CTEs (websearch_to_tsquery leg ORDER BY ts_rank_cd DESC; hnsw leg ORDER BY emb <=> q) -> RRF k=60 merge in a final CTE.
