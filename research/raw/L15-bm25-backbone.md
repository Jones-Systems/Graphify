## Scale math for our corpus (~200k docs / ~1M chunks)
- rank-bm25: query cost O(q_terms × 1M) Python-level ops ⇒ seconds/query [INFERENCE from implementation]; RAM for doc_freqs dicts ⇒ tens of GB ⇒ DISQUALIFIED.
- bm25s: index-time sparse-score build minutes-scale; queries ms-scale (12–1,196 QPS measured); fits if scores memmap'd.
- tantivy: inverted index over 5M-article Wikipedia <3 min on desktop hardware ⇒ [INFERENCE] our 1M chunks commit in well under 2 min on 16 EPYC cores; TOP-10 latencies in benchmark-game are µs–low-ms ⇒ ms-scale through PyO3 boundary.
- FTS5: 20k–150k docs/s build ⇒ 1M chunks ≈ 7–60 s; warm BM25 top-20 ≈ 5–30 ms typical, ≈12 ms reported @1M docs.
- RRF fusion adds <0.1 ms per query at k≤200 lists.

## VERDICT (≤3 lines)
Top pick: **tantivy-py** as BM25 backbone (`pip install tantivy==0.26.0`, cp313 wheels, MIT; never the stale `tantivy-py` squatter package): sub-ms–ms BM25 at 1M chunks, mmap keeps us above the 3 GiB floor, incremental commits; FTS5 is the zero-dependency fallback (~12 ms @1M docs, fixed k1/b) if a second compiled wheel is unwanted; reject rank-bm25 outright at this scale.
Integration sketch: per-repo tantivy schema {chunk_id u64 stored, path text stored+indexed, body text indexed} living beside graphifyy's node-link JSON; query path = tantivy BM25 top-100 ∥ dense-vector top-100 (future lane) → RRF(k=60, window 100) → top-k to reranker/graph expansion.
