## Context grounding (from Codex-V3 repo)
- **ENG-C11 Freshness contract** (`docs/migration/plans/graphify-v3-setup/research/spec-requirement-inventory.md:17`): deterministic `source_fingerprint` = SHA-256 over sorted canonical inventory (path/resolved/type/size/SHA-256) + effective ignore bytes + staging checksum + pinned identity; timestamps/run-names/caches excluded; classification is exactly `valid|stale|unknown`; stale/unknown must be disclosed with fallback to canonical source; navigation NEVER triggers refresh/network/credentials/mutation; per-source confirmation even when fingerprint is valid (refs LPRD:159,184-189; LENG:262-270).
- Current implementation: per-run immutable dirs hold `freshness.json` (`schema: graphify-v3-freshness/v1`, `tools/graphify/validate.py:129-136`); `promote.sh` gates on `validation.json`+`freshness.json` then `ln -sfn` repoints `$CORPUS/current`; WR-C16 mandates `os.replace` same-dir atomic swap; DEC-8 retains current + one prior validated run. So today's "ledger" is plain files + symlink repoint, made safe by ENG-C12 immutability and a serialized build lifecycle.
- Environment: single Debian 13 host (no network FS concern for WAL/LMDB shared-memory locks); MemAvailable floor 3072 MiB irrelevant at this data volume (thousands of rows across 18 corpora).

## Verdict (≤3 lines)
Top pick: the **hybrid** — SQLite (pin ≥3.53.4 amalgamation; Debian's 3.46.1 predates the WAL-reset corruption fix) in WAL mode, `synchronous=FULL`, `busy_timeout=5000` as the canonical per-corpus fingerprint/evidence ledger, while each validated run keeps its immutable `freshness.json` export for navigation compatibility. Integration sketch: `CREATE TABLE source_fingerprints(corpus TEXT, source_id TEXT, fingerprint TEXT, size INTEGER, resolved_path TEXT, run_id TEXT, PRIMARY KEY(corpus,source_id))` + `validation_evidence(id INTEGER PRIMARY KEY, corpus, run_id, checked_at_utc TEXT, status TEXT CHECK(status IN ('valid','stale','unknown')), detail_json TEXT)`; builders write via `BEGIN IMMEDIATE` (single-writer is fine — builds are serialized), navigators open `mode=ro`; staleness = SQL compare of recomputed fingerprint vs recorded row, missing/unparsable row ⇒ `unknown`, giving the exact tri-state contract. LMDB is the fallback only if a future hot-path cache needs lock-free readers with zero SQL; plain files demote permanently to export surface, never system of record.
