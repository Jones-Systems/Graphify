# LANE L36 — T6 local-llm: Ollama on 16c EPYC (Zen 4/Genoa), no GPU, MemAvailable ≥ 3072 MiB

Researched 2026-08-25. All sizes/dates verified against primary sources the same day.

## Host fit summary
- Target host: Debian 13, kernel 6.12, 16-core AMD EPYC (Genoa/Zen 4), **no usable GPU**, 64 GB RAM total, hard floor **MemAvailable ≥ 3072 MiB during any compute burst** (tantivy/LanceDB/Splink/GLiNER/bge-reranker already resident).
- Ollama runs CPU-only out of the box (AVX-512 present on Genoa). Current stable **v0.32.15** (released 19 Aug, GitHub-verified signature); v0.33.0 is at rc3 — do not deploy RCs. Release cadence is fast (multiple 0.32.x point releases within weeks), so pinning matters.
- Memory budget math: weights are mmap'd (file-backed/reclaimable) but decode touches every weight page each token; add ~300–600 MB Go-server/runner overhead + f16 KV cache @4096 ctx (≈150–350 MB for 1–2B GQA models). Rule of thumb: burst RSS ≈ weights×1.05 + 0.5 GB. Under the 3072 MiB floor, **keep model blobs ≤ ~2.5 GiB and only start a burst when ≥ 6.5–7 GB MemAvailable**; qwen3:4b (2.33 GiB) is the ceiling, everything larger (7B+) is out of scope for this host profile.
- Forward-looking cross-lane note: AMD shipped a ZenDNN GGML backend for llama.cpp on 2026-08-18 with ~2× prompt-processing gains on dense models, explicitly supporting EPYC 9004 "Genoa" — but decode still falls back to the native CPU path and it requires a custom `-DGGML_ZENDNN=ON` build; **not available through stock Ollama today**. Revisit only if prefill becomes the bottleneck.

## Verdict (≤3 lines)
Top pick: **qwen3:1.7b Q4_K_M pulled by manifest digest under Ollama v0.32.15 (stable)**, served with `OLLAMA_NUM_PARALLEL=1 OLLAMA_MAX_LOADED_MODELS=1 OLLAMA_CONTEXT_LENGTH=4096 OLLAMA_FLASH_ATTENTION=1 OLLAMA_KV_CACHE_TYPE=q8_0`, ~1.36 GB blob + ~0.5 GB runtime keeps the 3072 MiB MemAvailable floor safe; upgrade path qwen3:4b (2.33 GiB) once ≥6.5 GB headroom is measured. Integration sketch: run `ollama serve` as a systemd unit pinned to the v0.32.15 tarball; call the OpenAI-compatible `/v1/chat/completions` with `response_format=json_schema` (Pydantic entity/triplet schema, temperature 0) from the indexer pipeline; feed constrained-output triples into PPR-over-KG fusion and cross-validate against the existing Splink/GLiNER ER results — published evidence shows zero-shot small-LLM NER/RE is weak (≈11 F1) until schema-constrained and/or lightly fine-tuned (408 examples → 0.62 F1), so position the LLM as schema-guided relation extractor, not a GLiNER replacement.
