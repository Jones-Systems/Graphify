# Lane L69 — T11 Federation: Namespace/Prefix Strategy for Multi-Corpus Node IDs

Date: 2026-08-25. Lane: L69. Program phase: 1 (graph/semantic search upgrade, 18 VPS repos).
Stack: pinned graphifyy==0.9.16 structural graphs (NetworkX node-link JSON, one `graph.json` per corpus under `~/.agent-references/graphify/<corpus>/current/`), tantivy BM25, sqlite-vec, PPR-over-KG, gated 3-way RRF, Splink/GLiNER/RapidFuzz ER. Debian VPS, 16-core CPU-only, Python 3.13, MemAvailable floor 3072 MiB, offline/permissive only.

## Grounded local evidence

- **Current ID scheme is run-scoped path slugs.** Sampled node id from `~/.agent-references/graphify/codex-v3/runs/20260825T090340Z-full/graphify-out/graph.json`: `home_malcolmjones_agent_references_graphify_codex_v3_runs_20260825t090340z_full_staging_agents_md`. IDs are derived from the staging root passed to `gb.build(root=str(staging_root))` (`tools/graphify/offline_extract.py`), so they embed host path + run UTC timestamp + `staging`. **Every rebuild mints a disjoint ID space** — cross-run and cross-corpus joins on raw IDs are broken today, before federation even starts.
- **No namespace exists**: 18 corpora each have private flat string IDs. Same-named headings recur across repos (sampled labels "Purpose", "Outcome", "Examples" appear in multiple corpora), so naive global slug merging would create false entity collapses.
- **IDs are opaque downstream** (`tools/graphify/validate.py` does duplicate/end-point checks only, ENG-C7; upstream graphifyy itself distinguishes local vs global ids per the `local_id_mismatch` warning class, LENG ENG-C8). An index-layer remap touches neither the pinned library nor validators, and never mutates immutable run dirs (ENG-C12/D4 posture preserved).
- **Scale**: codex-v3 = 2,368 nodes / 4,661 edges (validation.json 2026-08-25); program estimate ~28.7k nodes / ~40.5k edges across 18 corpora. Measured extraction rate: pilot 155 files → 2,968 nodes in 1.8 s; full 18-corpus wave built sequentially in ~4 h wall including validation/promotion.
- **Collision math** (birthday approx., standard): truncated 64-bit hash over 2e6 federated nodes ⇒ p ≈ n²/2^65 ≈ 1.1×10⁻⁷; an 8-hex (32-bit) suffix is safe because it only disambiguates identical base keys (rare), not the whole keyspace.

## Verdict
Top pick: composite `(corpus_id, local_key)` namespacing at the load/index layer, rendered as CURIE `corpus:relative/path#slug@h8` — minted at ingestion from `source_file` + label slug, never mutating graph.json (keeps pinned graphifyy 0.9.16, ENG-C7/C12, D4 intact); reserve content hashes (blake3 1.0.9) for GLiNER/Splink ER-merged entity nodes only.
Integration sketch: loader parses each `<corpus>/current/graph.json`, maps raw ID → `(corpus, relpath#slug)` via a `node_key(corpus, local_key) INTEGER` surrogate table; cross-corpus edges land in `xedge(src_corpus, src_key, dst_corpus, dst_key, kind, evidence)` so PPR union is an integer join; alias table absorbs scheme changes forever.
Migration sketch: backfill aliases in one pass over ~28.7k nodes (seconds); rekey tantivy/sqlite-vec/PPR stores from the same graphs — at the measured 2,968-nodes/1.8 s extraction rate the whole reprocess stays well under an hour CPU-bound, versus the ~4 h full-wave baseline.

## Migration cost if the scheme changes later

- **The debt already exists**: run-timestamped IDs invalidate every ID-keyed artifact on every refresh. Adopting a stable scheme at ingestion converts a recurring per-refresh breakage into a one-time cutover — this is net-negative cost, i.e., fixing it saves work starting with the next weekly refresh.
- One-time cutover components: (a) loader rewrite ~100 LOC stdlib; (b) alias backfill 28.7k rows (trivial in SQLite); (c) rekey of BM25/vector/PPR stores from unchanged graphs (<1 h CPU at measured rates, RAM far below the 3072 MiB floor); (d) zero changes to graphifyy, validators, or run-dir layout.
- Future-proofing rule: keep the logical core (`corpus + relpath#slug`) fixed and vary only prefix/suffix policy — the alias table then absorbs any later change. Never promote content-hashes to primary key for mutable sources: that is the expensive-to-migrate case (every source edit cascades into edge repair), which is why hash-addressing scores AdoptCost 4 above.
- Cross-corpus edge impact: composite keys mean federation never rewrites per-corpus identities; same-named sections across repos ("Purpose", "Outcome" recur in many corpora — observed in sampled IDs) stay distinct unless ER explicitly emits an `xedge`, preventing false entity collapse.
