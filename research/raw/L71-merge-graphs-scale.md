## Verdict

Top pick: staged federation via `graphify global add <corpus>/current/graph.json --as <corpus>` per promoted run - free tag:: namespacing, label-deduped shared externals, atomic per-corpus refresh, unchanged-skip; avoid merge-graphs only when a static single artifact is explicitly needed, never the merge-driver at this scale.
Integration sketch: inside `build-graph.sh` promote step (after validate.py PASS), call `$ENV/bin/graphify global add "$RUN/graphify-out/graph.json" --as "$CORPUS"` under the existing mem_guard (warn<4096/halt<3072 MiB); document `~/.graphify/global-graph.json` as the federated read-only artifact; pre-set `GRAPHIFY_MAX_GRAPH_BYTES=2GB` in the wrapper (merged ~330-360 MB leaves only ~1.5x headroom under the 512 MiB default); keep PRD-C2 per-corpus routing and add union-at-fan-in validation (SPEC Section 3 already maps ENG-C7/C8 to it).

## Key mechanics (all read from installed 0.9.16 wheel, 2026-08-25)

1. Collision behavior: merge-graphs/global add relabel every node `repo_tag::local_id` (labels untouched, local_id attr recovers original, repo attr set) -> cross-corpus ID collisions impossible; same-stem input dirs get widened unique tags (#1729). Duplicate IDs WITHIN any single graph are ENG-C7 zero-tolerance FATAL in validate.py, so naive concatenation without prefixes can never pass promotion. Caveats: (a) only global add merges no-source_file external nodes by label (over-merge risk for identically-labeled distinct libs; edges rewired, remap self-loops dropped) while merge-graphs duplicates externals per repo (~inflates counts, fragments cross-repo paths); (b) both normalize to undirected simple Graph (#1606) - calls/inherits direction survives only in per-corpus graphs (affected, call-flow stay per-corpus); (c) labels stay unprefixed, so merged-query term seeding silently blends repos - node.repo enables attribution/filter, and navigate.md's PRD-C2 one-corpus rule remains the deliberate isolation guard.
2. Output size: measured 102.1 MB (73.8k n) / 116.4 MB (69.7k n) per-corpus; merged est 330-360 MB indent=2 including ~10% prefix/repo/local_id overhead [EST]; fits the 512 MiB per-file load cap (security.py _MAX_GRAPH_FILE_BYTES, overridable via GRAPHIFY_MAX_GRAPH_BYTES with MB/GB suffixes, re-read per call) with thin margin - corpus growth ~1.5-2x crosses it.
3. Query latency on merged graph: CLI query/path/explain fully reload + node_link_graph per invocation (cli.py:407-433; traversal itself is depth-2 BFS, negligible). For ~340 MB: json.loads ~2-4 s + graph rehydration ~similar again + O(N*terms) seed scan ~= 5-12 s cold per query [ESTIMATE - no execution in this read-only lane; query logging is opt-in default-off (#1797) so no measured latencies exist locally]. NetworkX docs position node-link JSON as interchange, not storage (dict-of-dict cost). Mitigations ranked: MCP serve residency (load once) > per-corpus routing > export-to-DB.
4. Practical limits: RAM peak during merge/global-add ~2.5-4 GB transient (source graphs + prefixed copy + accumulator + parsed JSON) [EST] -> must run inside existing mem_guard bands; merge-driver unusable >100k nodes/>50 MB inputs; HTML/wiki aggregation auto-skips >=5,000-node graphs (ENG-C6) so no merged HTML (harmless - nav consumes JSON); indent=2 inflates ~1.3-1.6x vs compact; pinned 0.9.16 trails PyPI latest 0.9.49 (fetched 2026-08-25; 448k dl/wk, YC S26, very active) - re-pin review is a separate decision.
