# Lane L39 — T6 local-llm: Structured-output reliability on local models (outlines/xgrammar/guidance + llama.cpp grammars)

**Question:** Do JSON-schema-constrained generations actually fix schema-invalid extractions at 3B–14B scale?

**Answer: YES for syntax/schema validity — decisively and cheaply. NO for semantic correctness.** Constrained decoding turns malformed/non-schema output into a near-zero event even at 1B–8B scale (XGrammar paper: function-call syntactic correctness 62% → 100%; JSONSchemaBench compliance 87–98% on function-calling schemas using **Llama-3.2-1B-Instruct** for coverage runs). On CPU the overhead is negligible-to-negative: JSONSchemaBench found constrained decoding was **up to 50% faster end-to-end than unconstrained** (no wasted malformed attempts/retries). But constraints never fix wrong values/hallucinated entities, engines **silently under-constrain** (XGrammar failed under-constraint checks in 38 of 105 feature categories; llama.cpp silently skips unsupported keywords like `patternProperties`, `uniqueItems`, `if/then/else`), and naive same-generation JSON-mode can tax reasoning ("The Format Tax", arXiv 2604.03616, Apr 2026: cost is mostly **prompt-level**, not decoder-level; recoverable via two-pass or CoT-in-schema). With schema-in-prompt + CoT field + post-validation, quality is neutral-to-positive at 8B (dottxt rebuttal, Llama-3-8B-Instruct: GSM8K 0.77→0.78, LastLetter 0.73→0.77, Shuffle 0.41→0.44 NL→structured; JSON 0.73 unconstrained → 0.77 constrained; JSONSchemaBench quality exp, Llama-3.1-8B-Instruct: LastLetters 50.7→51.2, Shuffle 52.6→52.7, GSM8K 80.1→83.7).

## Verdict
Top pick: **llama-server native json_schema (GBNF) + flat schemas + CoT-in-schema prompting + pydantic validate-and-retry (instructor-style)** — it eliminates schema-invalid extractions outright even with 1B-class models (93–98% compliance; 62→100% syntax in XGrammar's eval), costs ~nothing on our 16-core CPU box (constrained E2E measured *faster* than unconstrained), and needs zero cloud keys. Constraints fix syntax, not semantics: engines silently under-constrain (XGrammar 38 categories, llama.cpp keyword skips), so post-validate every payload against the original Draft2020-12 schema and retry ≤2× with the validator error; use the two-pass reason-then-format pattern only for hard multi-step extraction tasks.
Integration sketch: run `llama-server -m <qwen3-8b/q4_k_m>.gguf --port 8091` as a burst process (≈5 GB RSS mmap'd; 14B ≈9 GB also fits the 64 GB box if scheduled around the 3 GiB MemAvailable floor); POST /v1/chat/completions with response_format=json_schema built from the existing Pydantic extraction models (flatten: explicit properties/required, enums, additionalProperties:false, bounded arrays; avoid $ref nests/patterns/unions that llama.cpp skips or Outlines chokes compiling); validate with `Model.model_validate_json(...)` + extra="forbid"; on failure append the pydantic error and retry ≤2×, then fall back to the existing GLiNER/RapidFuzz path and log; A/B extraction-F1 constrained-vs-unconstrained on a golden set before rollout (expected neutral-to-positive per 8B quality evidence). Skip torch-dependent XGrammar and guidance/llguidance initially; add guidance only if a specific gnarly schema fails to compile in llama.cpp.
