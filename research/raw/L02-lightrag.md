# Lane L02 (T1 graphrag) — LightRAG (HKUDS) deep-dive
Date: 2026-08-25 · Scope: incremental-update claims vs Microsoft GraphRAG, real local-run reports, license, feasibility of mounting OUR graphifyy graph.json under LightRAG's retrieval layer instead of its own extraction.

## Verified facts

**Identity / maturity.** PyPI `lightrag-hku` **1.5.6** (latest, checked 2026-08-25), Python >=3.10, MIT license, ~86K weekly downloads. Repo HKUDS/LightRAG: **39,165 stars / 5,504 forks**, EMNLP2025 paper (arXiv 2410.05779, v3 dated 2025-04-28). Release activity continuous: news entries through **2026.07** (Smart Heading for docx); 2026.05 merged RAG-Anything multimodal pipeline + 4 chunking strategies + role-specific LLM config; 2026.03 OpenSearch backend + setup wizard; 2025.10 large-scale scalability rework; 2025.09 improved KG extraction for open-source LLMs (Qwen3-30B-A3B); 2025.08 reranker support (now default in mix mode) + document deletion with automatic KG regeneration.

**Incremental-update claims vs GraphRAG (paper §4.5/RQ4, Legal dataset, GPT-4o-mini).**
- Retrieval phase: GraphRAG consumed **610×1,000 tokens** (610 level-2 community reports × ~1k tok) plus hundreds of API calls for community traversal; LightRAG used **<100 tokens and 1 API call** (keyword generation + vector/graph match).
- Incremental update: adding a same-size corpus forces GraphRAG to dismantle and fully regenerate communities ≈ **1,399 communities × 2 × 5,000 tokens ≈ 14M tokens**, while LightRAG pays only the new docs' extraction cost T_extract and merges node/edge sets by union (paper §3.1 “Fast Adaptation to Incremental Knowledge Base”). Claim independently stated in abstract and README (“Incremental Updates & Selective Deletion … LLM cache created during indexing to quickly rebuild the affected entities”).
- Quality vs GraphRAG is NOT a blowout: win-rates (README table, mirrors paper Table 1) Overall Agriculture 54.8 / CS 52.0 / Legal 52.8 / **Mix 49.6 (parity)** — biggest edge is **Diversity** (59–77%), i.e., LightRAG's honest pitch is cost+freshness, marginal quality.

**Local-run reality (CPU-only VPS, no GPU, 16 cores, ≥3 GiB free-RAM floor).**
- Issue #174 (HKUDS/LightRAG): indexing with `llama3.2:1b` via Ollama effectively stalled; `gemma2:2b` and `qwen2.5:7b` completed. Sub-7B models produce malformed extractions → retries/stalls.
- Maintainer troubleshooting (README): models below ~50 tok/s risk extraction timeouts (`EXTRACT_LLM_TIMEOUT`, effective timeout = 2× configured); local Qwen models occasionally loop endlessly; keep `OLLAMA_KEEP_ALIVE=-1`; start with MAX_ASYNC_LLM=1 / MAX_PARALLEL_INSERT=1 on one local model; dedicated embedding model (never the chat model): `nomic-embed-text` (768d) or **`bge-m3`** (1024d, README's local pick); embedding choice is frozen once indexed (no re-embed tool).
- README claims high RAG quality “even when paired with a 30B open-source LLM” and recommends local reranker `bge-reranker-v2-m3` (+1–2 s latency). On our RAM floor, a Q4 7B model (~4.7 GB weights + KV) breaks the 3072 MiB MemAvailable floor if co-resident with other work; realistic local profile is a 4B-class instruct model or scheduled batch indexing windows. Cloud LLM keys would need owner flag (`requires-owner-approval`).
- Default storages are **in-memory with local file persistence** (JsonKVStorage, NanoVectorDBStorage, NetworkXStorage, JsonDocStatusStorage) — fine for dev-scale corpora, RAM-bounded; Postgres/Mongo/OpenSearch all-in-one exist for production. Fully offline deployment path documented (docs/OfflineDeployment.md).

**Can the retrieval layer sit on OUR graph.json? YES — two paths.**
- **Path A (supported API): `rag.insert_custom_kg()`** (examples/insert_custom_kg.py, verified today). Accepts dicts: entities `{entity_name, entity_type, description, source_id}`, relationships `{src_id, tgt_id, description, keywords, weight, source_id}`, chunks `{content, source_id}`. We convert graphifyy node-link JSON → this schema (node name→entity_name; AST/markdown titles→entity_type; synthesized description from node attrs/context; edges→relationships with keywords=link/anchor text). Import embeds names/descriptions/chunks (local bge-m3 suffices); no LLM extraction pass needed. Caveat: global/high-level mode ranks relations largely by their description/keyword vectors — bare structural edges with empty descriptions will rank poorly, so edge-text synthesis is load-bearing.
- **Path B (adapter): custom `GRAPH_STORAGE` subclass** of BaseGraphStorage reading our node-link JSON live (supported injection point — `graph_storage` param; built-ins: NetworkXStorage, Neo4JStorage, PGGraphStorage, PGTableGraphStorage, AGEStorage, OpenSearchGraphStorage). [INFERENCE] ~200–300 LOC mirroring NetworkXStorage; but SDK/core marked “experimental, may not be compatible with future versions”, and the project had major storage refactors in 2025–2026 → maintenance risk. Path A is the low-risk route; Path B only if live-mount freshness matters.
- What you give up by skipping LightRAG extraction: LLM entity profiling/gleaning and dedup — which is where most of its quality comes from. With a purely imported structural graph, expect behavior closer to “vector-indexed link-graph traversal”; chunk insertion (original md/code chunks alongside the KG) keeps naive/mix modes strong.

## Verdict
Top pick: adopt `lightrag-hku==1.5.6` behind `lightrag-server` fully local (Ollama 4B-class extractor + bge-m3 + bge-reranker-v2-m3), ingesting our raw md/code corpora so ITS extraction builds the semantic layer; use `insert_custom_kg` to ALSO mount our existing graphifyy graph.json (nodes→entities, edges→relationships with synthesized descriptions) rather than forcing its retrieval layer onto our file via an experimental storage adapter. Integration sketch: converter script node-link-JSON → custom-KG dict → `insert_custom_kg` into same workspace as corpus-derived KG; query via mix mode; incremental inserts keep updates cheap (the GraphRAG rebuild tax is exactly what we avoid). Its headline advantage over GraphRAG is efficiency/freshness (retrieval <100 tok vs 610k tok; updates skip 14M-token community rebuilds), with only marginal quality deltas (Mix overall 49.6% parity) — so treat as infrastructure upgrade, not quality silver bullet.
