# LANE L65 — T10 eval: RAGAS/TruLens-class metrics WITHOUT cloud APIs (CPU-only survival)

Checked 2026-08-25. Constraints applied: Debian VPS, 16 CPU cores, no GPU, MemAvailable ≥ 3072 MiB during bursts, Python 3.13, offline/permissive preferred.

## Bottom line
Three of the four canonical RAG metric families survive CPU-only fully: (1) **context precision/recall** → deterministic IR metrics (ranx) over qrels, zero model calls; (2) **faithfulness/groundedness** → small NLI/cross-encoder factuality scorers (MiniCheck-Flan-T5-large ~770M, HHEM-2.1-Open ~110M) that match or approach GPT-4-judge correlation on LLM-AggreFact at <1B params; (3) **answer relevance** → embedding-cosine / reranker scores from weights already in our stack. The LLM-judge tier (RAGAS Faithfulness/ResponseRelevancy prompts, DeepEval G-Eval-style) is *runnable* offline via any OpenAI-compatible local server (llama.cpp/Ollama), but a 3B judge is noisy and slow (~20–35 tok/s): use it as a periodic audit sample (~50–200 queries), not the primary loop.

## What does NOT survive CPU-only (do not build on)
- Cloud-judge defaults everywhere: RAGAS/DeepEval/Phoenix out-of-box configs target gpt-4o-mini-class judges; without a local server they are dead weight.
- G-Eval-style CoT judging at scale on 16 cores: a 3B judge at ~20–35 tok/s × multi-call metrics ≈ minutes per query — restrict to audit samples (50–200 queries), never CI loops.
- LangSmith/LangFuse-cloud/Confident-AI cloud dashboards — cloud-bound, excluded (would be `requires-owner-approval`).
- Judge weights >4B params: breach the MemAvailable floor when co-running with indexing/embedding bursts.

## Verdict
Top pick: a layered offline harness — ranx over gold qrels for context precision/recall (deterministic, instant), HHEM-2.1-Open + MiniCheck-Flan-T5-large ensemble for faithfulness, and in-stack bge-reranker/embedding cosine for answer relevance; reserve ragas-with-local-judge (llama.cpp, Qwen2.5-3B pending owner approval or Phi-3.5-mini MIT) as a quarterly ~100-query audit tier.
Integration sketch: export tantivy/sqlite-vec retrieval results to ranx Run dicts against hand-seeded qrels JSONL (seed labels by running MiniCheck on question↔chunk pairs); split answers into sentences, batch-score vs concatenated retrieved context with HHEM→MiniCheck fallback disagreement flagging; write per-metric columns into the existing sqlite eval DB keyed by query_id so fusion-weight tuning (gated 3-way RRF) can regress against them.
RAM discipline: run the llama.cpp judge phase exclusively (n_ctx 4096, threads 8, no concurrent graphify/tantivy builds) to hold MemAvailable ≥ 3072 MiB; HHEM (439 MB) and MiniCheck (≈3 GB fp32 on disk, less resident with batching) each get their own sequential window.
